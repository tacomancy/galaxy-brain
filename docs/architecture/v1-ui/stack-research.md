# Workbench V1 desktop stack decision brief

Status: accepted through [ADR 0004](../../adr/0004-use-electron-typescript-for-v1.md)  
Date: 2026-08-26  
Evidence policy: current first-party project documentation, accessed 2026-08-26

## Question and constraints

Choose the smallest responsible stack for a macOS-only V1 Knowledge Workbench while preserving a credible path to Windows and Linux. The application must open or scaffold an arbitrary user-selected Galaxy Brain repository, make the rendered desktop application automatable at the confirmed S1 Test Seam, and leave room for rich/source editing and deep PDF processing without requiring Git or network services.

The decision is about the production foundation, not the disposable prototype. It should preserve the accepted application Modules and Test Seams rather than turn framework objects, routes, editor nodes, or storage paths into Interfaces.

## Recommendation

Use **Electron with a React and strict-TypeScript renderer**, built and packaged by **Electron Forge's Webpack TypeScript integration**. Use **WebdriverIO with `@wdio/electron-service` for S1 desktop workflow tests** and **Vitest for S2-S5 application and Adapter behavior tests**.

Electron embeds Chromium and Node.js and supports macOS, Windows, and Linux from one JavaScript codebase. That gives the Workbench one language and package ecosystem across UI, application Modules, the production repository Adapter, and test Adapters while retaining a cross-platform shell. [Electron introduction](https://www.electronjs.org/docs/latest/)

## Electron versus Tauri 2

Tauri 2 is a credible alternative. Its current testing story no longer has the historical macOS blocker: Tauri now recommends WebdriverIO with `@wdio/tauri-service`, whose embedded WebDriver server works on macOS, Windows, and Linux. Direct `tauri-driver` remains limited to Windows and Linux because macOS has no native desktop WKWebView driver. [Tauri WebDriver testing](https://v2.tauri.app/develop/tests/webdriver/) · [Tauri test overview](https://v2.tauri.app/develop/tests/)

| Criterion | Electron | Tauri 2 | Assessment for this Workbench |
| --- | --- | --- | --- |
| macOS S1 automation | WebdriverIO's Electron service launches compiled or Forge applications, configures ChromeDriver, accesses Electron APIs, and mocks Electron system APIs. [WebdriverIO Electron](https://webdriver.io/docs/desktop-testing/electron/) | WebdriverIO supports macOS through an embedded WebDriver server. Advanced execution, mocking, and logs require `tauri-plugin-wdio`; the embedded macOS provider additionally requires `tauri-plugin-wdio-webdriver`. The service documentation classifies these as test-only and says to exclude them from production builds. [Tauri WebDriver](https://v2.tauri.app/develop/tests/webdriver/) · [Tauri plugin setup](https://webdriver.io/docs/desktop-testing/tauri/plugin-setup/) | Both satisfy S1. Electron has the smaller testing/toolchain surface for a TypeScript-first repository. |
| Playwright alternative | Playwright can launch Electron and expose windows and the main process, but its official API still labels Electron support experimental and cannot intercept native Electron dialogs without main-process replacement. [Playwright Electron](https://playwright.dev/docs/api/class-electron) | Playwright is not Tauri's recommended desktop path; Tauri documents WebdriverIO/WebDriver. [Tauri WebDriver](https://v2.tauri.app/develop/tests/webdriver/) | Do **not** use Playwright for S1 initially. WebdriverIO is the explicit S1 choice for both framework candidates and avoids basing a core Test Seam on Playwright's experimental Electron API. |
| repository access | The main process can present a native directory picker and use stable Node filesystem APIs. [Electron dialog](https://www.electronjs.org/docs/latest/api/dialog) · [Node filesystem](https://nodejs.org/api/fs.html) | Tauri's filesystem plugin is default-deny: permissions and explicit path scopes are both required, and path traversal is rejected. [Tauri filesystem plugin](https://v2.tauri.app/plugin/file-system/) | Tauri has the stronger default permission model. Electron is simpler for a repository-centric application but must enforce a narrow root-scoped Interface itself. |
| renderer security | Electron defaults to context isolation and renderer sandboxing, but its main process has Node authority. Electron requires a narrow preload bridge, IPC-sender validation, a restrictive CSP, no renderer Node integration, and no remote code. [Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security) · [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation) | Tauri capabilities constrain which commands each window or WebView may invoke, and dangerous filesystem operations are blocked until permissions and scopes are granted. [Tauri capabilities](https://tauri.app/security/capabilities/) · [Tauri filesystem permissions](https://v2.tauri.app/plugin/file-system/) | Tauri wins on secure defaults. Electron is acceptable only with the mandatory boundaries below. |
| application toolchain | Chromium, Node, application Modules, and repository Adapter can all be authored and tested in TypeScript. [Electron introduction](https://www.electronjs.org/docs/latest/) | Tauri combines an HTML/JavaScript WebView frontend with a Rust backend connected through message passing and requires Rust for development. [Tauri architecture](https://v2.tauri.app/concept/architecture/) · [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) | Electron better preserves locality for the current repository and first tracer bullets; Tauri adds a second language and build graph before a demonstrated need. |
| rendering consistency | Electron ships its Chromium runtime. [Electron introduction](https://www.electronjs.org/docs/latest/) | Tauri uses the operating system WebView and does not ship a browser runtime. [Tauri architecture](https://v2.tauri.app/concept/architecture/) | **Inference — agent:** Electron reduces cross-platform engine variation for later rich editing and PDF work. Tauri's approach yields smaller binaries but makes WebView differences part of future platform qualification. |
| application size | Electron distributes its embedded Chromium and Node runtime. [Electron introduction](https://www.electronjs.org/docs/latest/) | Tauri uses the OS WebView and documents small compiled binaries. [Tauri architecture](https://v2.tauri.app/concept/architecture/) · [Tauri app size](https://v2.tauri.app/concept/size/) | Tauri wins. V1 has no accepted bundle-size requirement, so this does not outweigh toolchain and renderer consistency. |
| packaging and cross-platform path | Electron supports macOS, Windows, and Linux; Forge produces platform-specific distributables and macOS DMGs. [Electron introduction](https://www.electronjs.org/docs/latest/) · [Forge makers](https://www.electronforge.io/config/makers) | Tauri builds for macOS, Windows, and Linux and supports signed/notarized macOS app bundles and DMGs. [Tauri architecture](https://v2.tauri.app/concept/architecture/) · [Tauri distribution](https://v2.tauri.app/distribute/) | Both preserve a credible cross-platform path. Neither eliminates the need to test and package on each future target OS. |

**Decision:** Electron wins for V1 because its advantages align with the first required behaviors, while Tauri's strongest benefits—smaller binaries and default-deny native capabilities—are not currently acceptance criteria. Confidence is **moderate-high**. Revisit Tauri only if measured Electron footprint or resource use becomes unacceptable, the project gains sustained Rust ownership, or OS-WebView variation becomes an accepted cost.

## Why not a browser or PWA

A browser application is technically capable of opening a user-selected directory on supporting browsers. It is not an equivalent foundation for this V1. The File System Access API requires a secure context, user activation, and explicit permission; access and persistence are mediated by the browser, and the API cannot be completely polyfilled. [Chrome File System Access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)

The Workbench is explicitly a desktop product whose S1 seam exercises a rendered desktop application and whose production repository Adapter must reopen and monitor arbitrary repositories. A PWA would make the browser, its permission lifecycle, and its feature support part of that Interface, while still requiring a separate solution for deterministic desktop automation and distribution. **Inference — agent:** that is more platform uncertainty, not less, for the accepted V1. Reject a PWA as the production shell; renderer-only browser runs may still be used as fast feedback, but never as S1 evidence.

## Mandatory Electron boundaries

Electron's simpler filesystem access must not become renderer-wide authority:

1. The **main process** owns the selected repository root and the production Knowledge Repository Adapter. A native `openDirectory` dialog supplies the initial user choice. [Electron dialog](https://www.electronjs.org/docs/latest/api/dialog)
2. The **renderer** runs with Node integration disabled, context isolation and sandboxing enabled, and a restrictive CSP. It loads packaged local application content only. Electron recommends these settings and warns against executing remote code with Node integration. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security)
3. A **preload Adapter** exposes small, typed, operation-specific methods through `contextBridge`; it never exposes `ipcRenderer`, filesystem primitives, paths, or a generic command channel. Electron's preload guidance demonstrates wrapping individual IPC operations rather than exposing the IPC module. [Electron preload guidance](https://www.electronjs.org/docs/latest/tutorial/tutorial-preload) · [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)
4. Every privileged handler validates the IPC sender and validates requested logical paths against the canonical selected root, including symlink behavior. Electron explicitly requires sender validation. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security)
5. Serve application assets through a controlled custom scheme instead of granting `file://` privileges. Electron recommends custom protocols because `file://` can expose local files more broadly. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security)
6. Keep session configuration, linked-local paths, hashes, and machine-local rollback indexes outside the portable Repository Format. The repository stores portable Source Records and logical Source Locators, consistent with the accepted architecture.

These are architectural constraints, not optional hardening tasks. The renderer-to-preload bridge is an Adapter around Electron desktop capabilities; it must not become the Knowledge Repository Interface or move application rules into IPC handlers.

## TDD consequences

- **Tracer Bullet 1 / S1:** WebdriverIO launches the compiled Electron application and operates Atlas through accessible names and visible outcomes. It uses the real Workbench-owned Modules and the in-memory file-semantics Adapter. It does not inspect React state, routes, or storage.
- **S2-S4:** Vitest calls the confirmed Module Interfaces with literal fixtures and Independent Expected Values.
- **S5:** the same Vitest contract suite runs against the in-memory and file-backed Knowledge Repository Adapters; later, the PDF contract suite runs against its fixture and production Adapters. Git and Git LFS are outside the V1 application boundary.
- **True desktop seams:** WebdriverIO may replace a native dialog response or another Electron API only when the behavior under test crosses that External System Seam. WebdriverIO documents Electron API mocking; Workbench-owned Modules remain real. [WebdriverIO Electron mocking](https://webdriver.io/docs/desktop-testing/electron/mocking/)
- **Accessibility:** S1 selectors should prefer accessible names and assert visible focus and semantics where those are the Public Behavior. Static JSX lint and automated checks supplement but do not replace keyboard and assistive-technology review. [WebdriverIO best practices](https://webdriver.io/docs/bestpractices/) · [JSX accessibility lint limitations](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y)

## Risks to validate in the first slices

1. Run Tracer Bullet 1 against the compiled app with WebdriverIO before treating the harness as established; `@wdio/electron-service` is documented in the WebdriverIO ecosystem but its service reference identifies it as a third-party package. [WebdriverIO Electron service](https://webdriver.io/docs/wdio-electron-service/)
2. Verify a packaged `.app` in addition to development launch before the first release checkpoint; packaging and development have different paths and security settings. Forge's `make` flow first packages the application and then creates the distributable. [Electron Forge packaging flow](https://www.electronjs.org/docs/latest/tutorial/tutorial-packaging)
3. Add a repository-root threat model before enabling writes: path normalization, symlinks, atomic updates, external modifications, fingerprints, rollback, and partial failures are production Adapter concerns that S5 must make observable without freezing filenames or layout.
4. Budget continuous Electron upgrades. Electron supports only its latest three stable releases and explicitly recommends staying current for security. [Electron release policy](https://www.electronjs.org/docs/latest/tutorial/electron-timelines) · [Electron security](https://www.electronjs.org/docs/latest/tutorial/security)
5. Treat signing credentials and notarization as CI secrets; do not delay a signed-package smoke test until the end of V1. Electron documents signing as part of trusted distribution. [Electron distribution](https://www.electronjs.org/docs/latest/tutorial/distribution-overview)
